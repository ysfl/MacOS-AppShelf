# 文档结构

本目录按**时效性**分层。分层的目的只有一个：让下一个人和下一个 agent 知道哪份文件是
现在的真相，哪份只是当时的记录。

| 层 | 位置 | 时效 | 谁能引用它 |
|---|---|---|---|
| 规范 | `docs/standards/` | 长期有效，无日期后缀 | 门禁脚本、代码注释、README |
| 台账 | `docs/ledger/` | 只追加，条目可标失效 | 门禁脚本、评审 |
| 快照 | `docs/reports/` | 一次性，文件名带日期 | 只被自己那一轮的提交说明引用 |

## 生命周期规则

1. **规范被脚本引用**。`docs/standards/` 里写的阈值和禁则，必须能在
   `Scripts/gates/gates.py` 找到对应实现；写了却没有实现的规范，等于没有规范。
2. **台账只追加不重写**。一条坑位被修好后不删行，改状态；同一形态复发时在原行上追加，
   而不是新开一条让人以为是新问题。
3. **快照会过期**。带日期的评估报告完成后，把仍然成立的结论搬进规范或台账，然后它就不再
   是入口。不要在新文档里引用快照的结论而不注明它可能已经过时。
4. **禁止双体系**。同一件事只能有一个真相源。提交格式看 `standards/engineering.md`，
   不要另开一份。
5. **改动前先说影响哪份文档**。收口时要么更新文档，要么明确写出"本次改动对文档无影响"
   的理由，不留模糊状态。

## 反模式

- 用修改记录、审计快照充当现行规范。
- 规范写了一套、代码和门禁执行另一套。
- 台账条目指向不存在的测试（`traps-ledger` 检查会拦）。
- 把内部工作区的内容、命名或路径写进本仓库（`publication` 检查会拦，见
  `standards/publication.md`）。
