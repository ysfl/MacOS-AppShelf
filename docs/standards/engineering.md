# 提交与实现规范

## 提交信息

类型前缀取以下之一，标题不超过 72 字符，末尾不加标点：

`feat` `fix` `refactor` `perf` `test` `docs` `build` `ci` `chore`

正文必须回答**为什么**，而不是复述 diff。`docs:` `chore:` `ci:` 可以只有标题。

由 `.githooks/commit-msg` 硬拦；`pre-push` 会对推送范围内的**每一个**提交重跑一遍，
因为本地钩子可以被绕过，而一次推送常常跨多个提交。

## 一次改动一个关注点

按关注点提交，并且**做完一个就提交一个**，不要攒到最后。攒到最后的结果是重构与修复
混在同一批文件里，拆开会产生无法编译的中间提交，只能塞成一个巨型提交，谁也没法审。

如果确实无法拆分，在提交说明里写清为什么。

## 注释

- 默认不写。写的时候只写**为什么**：隐藏的约束、微妙的不变量、某个写法针对的具体缺陷、
  会让读的人意外的行为。
- 不解释代码在做什么——命名好的标识符已经说明了。
- 不写"用于 X 流程""为 issue #123 添加"这类会随代码演化腐烂的话，那些属于提交说明。
- 多行注释压到一行，不写多段文档块。

## 真实实现约束

交付必须可运行、可接线、可验证。禁止以下撑场面的写法：

- 残留 `TODO` / `FIXME` / `XXX` / `HACK`；
- 抛"未实现"来冒充已接线；
- 返回 mock / fake / stub / dummy 或固定成功响应；
- 空分支、没有接上的回调入口；
- 用假数据充当正式运行依赖；
- 只在记录里声称完成，代码里没有。

测试目录与夹具里的替身是合法的，但必须与正式实现隔离存放。临时的兼容代码必须真实可执行，
并写明原因、适用范围和移除条件。

由 `no-stubs` 检查在 `Sources/` 与 `Scripts/` 上硬拦（该检查不扫自身，因为它自己的规则表
里就带着这些词）。

## 不写不会用到的东西

不预留"以后可能用"的参数、开关、抽象层和回退分支。三处重复好过过早抽象。
加了又没用的代码，本仓库的门禁不会拦，靠评审。
